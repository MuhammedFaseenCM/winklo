# Stats and achievements (area D) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upload each player's local daily history once, show per-game stats (with a time histogram, a calendar of cleared days and a personal-best trend), and award achievements on Profile with a one-time banner on Results.

**Architecture:** Every number on the new screens comes from pure functions in `lib/domain/stats/` and `lib/domain/achievements/`, fed by one use case (`LoadGameHistory`) that merges `users/{uid}/game_days` with the local history using the existing `mergeGameDay`. The one-time upload is its own use case (`UploadProgressHistory`) that `SyncProgress` calls at the end of a full, signed-in run. The UI is new files under `lib/features/stats/` and `lib/features/achievements/`; the hotspot files get one or two lines each.

**Tech Stack:** Flutter, flutter_bloc (Cubit), go_router, cloud_firestore, shared_preferences, mocktail, bloc_test. Charts are `CustomPainter`s; no new packages.

Spec: `docs/superpowers/specs/2026-10-15-roadmap-batch-design.md`, section D.

## Decisions (where the spec leaves room)

- **Daily keys only.** History is read from `best_time_{modeKey}` (plus `best_pts_`, `clear_meta_`, `clear_board_`, `hints_used_`) where `modeKey` is `zip_daily_{playId}`, `path_words_{playId}` or `sudoku_{playId}` and `playId` matches `^[0-9]{8}([0-9]{4})?$`. So `zip_archive_…`, `path_words_practice` and the like (area F) never match.
- **What the upload writes.** For each local clear: `merged = mergeGameDay(local, remote)` with legacy flags. It's written when the remote doc is missing or differs from `merged`. `merged` never regresses the remote copy, so it satisfies `gameDayDoesNotRegress`. Writes go in batches of 400. When the rules reject a batch (`permission-denied`), its docs are written one at a time and the rejected ones are skipped. Other errors (offline, timeout) leave the flag unset, so the next full sync retries. `clearedAt` is left unset for days the upload creates, because the real clear time is unknown.
- **The flag** is `history_uploaded_{uid}` (a bool in prefs). Its prefix isn't a user-progress prefix, so a purge on account switch keeps each uid's flag.
- **Rules:** `validGameDay` already accepts any `playId` of the right shape, with no date window, so old days are allowed and **the rules don't change**. A rules test pins that there is no date-window check.
- **Streaks on the stats screen** are the stored streak (decayed for today, as Home shows it). Longest is `max(stored longest, longest run of consecutive cleared days)`. Achievements use the same longest.
- **Hint-free** means `usedHints == false`, falling back to `hintsUsed == 0` when the flag is missing. **Flawless** means hint-free and `hadMistakes == false`, so legacy Sudoku clears (where `hadMistakes` is guessed as true) don't count.
- **Histogram:** 5 buckets. The step is the smallest "nice" one (5 s, 10 s, 15 s, 20 s, 30 s, 1 m, 90 s, 2 m, 3 m, 5 m, 10 m, 15 m, 30 m, 1 h) for which the first four buckets reach past the 90th percentile. The fifth bucket is open-ended ("4:00+"), so one slow outlier doesn't flatten the chart.
- **Trend:** 30 daily points (today − 29 … today). Each point has the day's time (or none) and the running all-time best as of that day. The trend is empty when there's no clear in the window.
- **Calendar:** months from the first cleared month to the current month, shown one month at a time with a pager (the newest month first). The week starts on `MaterialLocalizations.firstDayOfWeekIndex`.
- **The seen set** is `achievements_seen` (a string list in prefs). `achievements_` is added to `userProgressKeyPrefixes`, so the set moves with the local progress owner (it's purged or stashed on an account switch). On the first Results after the update, every badge unlocked so far shows once ("3 new badges").
- **Optional providers:** the Profile section and the Results banner read their use case with `context.read<T?>()` and render nothing when it's absent, as Profile already does for `HapticsService?`. Existing screen tests keep working unchanged.
- **Debug periods** (`YYYYMMDDHHmm`) collapse to their date for the calendar, streak runs, trend and the perfect day.
